# Inbox Zero — personal deployment

Run [Inbox Zero](https://github.com/elie222/inbox-zero) for one person on Oduflow. PostgreSQL stays
in Oduflow's managed database plane. The application and its scheduled jobs share one container;
Redis and a small Upstash-compatible HTTP bridge run as private supporting services. The queue
itself remains in-process (`QUEUE_BACKEND=internal`).

This stack creates:

- **Inbox Zero 2.30.0**, published as `inbox-zero.<your-domain>`;
- **a managed PostgreSQL database**, with its generated URL injected without storing it in YAML;
- **authenticated Redis 7**, with AOF data on a persistent managed volume;
- **an Upstash-compatible HTTP bridge**, used by Inbox Zero's Redis client;
- **a runtime volume** containing generated auth, encryption, internal API, and cron secrets;
- **an Odoo 19 environment** named `inbox-zero-stack`. Stack V1 requires one Odoo target; this
  checkout also provides the source context for optional wrapper-image builds. Inbox Zero does not
  use the Odoo database.

## Configure secrets and integrations

Create a Google OAuth application, enable the Gmail and People APIs, and create the Gmail Pub/Sub
topic/subscription described by Inbox Zero. The OAuth callback and Pub/Sub push URL must use the
same public origin as `INBOX_ZERO_BASE_URL`.

```bash
cp .env.example .env
# Fill every empty value and replace the example URLs/identifiers.
```

The example uses Oduflow named-secret references. Create those secrets before applying the stack:

- `zeroinbox-google-client-secret` — Google OAuth client secret;
- `zeroinbox-google-pubsub-token` — any private random string, also configured on the Pub/Sub push
  subscription;
- `zeroinbox-redis-token` — a long random Redis/bridge token;
- `zeroinbox-litellm-key` — the API key accepted by the private LiteLLM endpoint;
- `zeroinbox-telegram-bot-token` and `zeroinbox-telegram-webhook-secret` — required only when the
  Telegram channel is enabled.

`REDIS_HOST` and `UPSTASH_REDIS_URL` contain Oduflow's deterministic service container names.
Replace the `1` in both values when applying with another team ID. Stack V1 does not yet provide a
cross-service container-name reference.

For a private LiteLLM proxy, keep `DEFAULT_LLM_PROVIDER=openai-compatible`, set
`OPENAI_COMPATIBLE_BASE_URL` to its OpenAI-compatible `/v1` URL, and use the exact model alias
returned by that proxy in `DEFAULT_LLM_MODEL`.

Keep `.env` out of Git. Runtime secrets generated by `runtime.sh` stay in the managed volume and
survive service updates. Back up that volume together with the database: changing
`EMAIL_ENCRYPT_SECRET` would make stored provider credentials unreadable.

## Apply

Run on the Oduflow server:

```bash
git clone https://github.com/oduflow/oduflow-stacks.git
cd oduflow-stacks/inbox-zero
cp .env.example .env
# Edit .env first.

oduflow stack validate oduflow.yaml
oduflow stack plan oduflow.yaml --team 1
oduflow stack apply oduflow.yaml --team 1
```

Open the service URL shown by Stack apply or on the Services page. `AUTH_ALLOWED_EMAILS` admits only
the address in `INBOX_ZERO_OWNER_EMAIL`.

The Redis services intentionally declare the unused port `8888`, because Oduflow currently
requires every auxiliary service to have an exposure target. Redis still listens only on its
private container port `6379`; the HTTP bridge listens only on private port `80`. Their generated
Traefik hostnames therefore lead to no application listener and do not publish either backing
service.

If Telegram is enabled, create a bot with BotFather and register this webhook with Telegram:

```text
https://inbox-zero.example.com/api/telegram/events
```

Pass the value stored in `zeroinbox-telegram-webhook-secret` as Telegram's `secret_token`. The
Telegram item appears in Inbox Zero's channel list whenever both Telegram environment variables
are present. Registering the webhook is still required for messages to arrive.

The database declared by Stack V1 is placed on the shared development PostgreSQL cluster. For a
long-lived installation with WAL-G coverage, create it explicitly on the production cluster and
deploy the service through the Oduflow service tools instead:

```bash
oduflow call create_service_database '{"name":"inbox-zero","cluster":"prod"}'
```

## Optional: publish the one-file wrapper image

The manifest deliberately uses the unmodified upstream image plus `runtime.sh` from a volume, so it
is portable across registries. To publish a self-contained equivalent into the registry configured
for your Oduflow team, apply the Stack first and build from its checkout:

```bash
oduflow call start_image_build '{
  "env_name":"inbox-zero-stack",
  "context":"inbox-zero",
  "dockerfile":"Dockerfile",
  "build_args":"INBOX_ZERO_VERSION=2.30.0"
}'

# Poll the returned build id, then publish the exact successful image:
oduflow call get_image_build '{"env_name":"inbox-zero-stack","build_id":"<build-id>"}'
oduflow call publish_image_build '{
  "env_name":"inbox-zero-stack",
  "build_id":"<build-id>",
  "repository":"inbox-zero",
  "tags":"2.30.0-oduflow.1"
}'
```

You can then update the service to the published image and remove the command and script mount. Keep
the runtime volume mounted at `/var/lib/inbox-zero-runtime`.

## Operations

The image runs Prisma migrations before starting Next.js. The wrapper waits for the web process and
then schedules the same maintenance endpoints as the upstream Docker Compose deployment. If the web
process exits, the wrapper stops its cron loops and lets Docker restart the service.

Useful checks:

```bash
oduflow call get_service_info inbox-zero
oduflow call get_service_logs inbox-zero 200
oduflow call get_service_info inbox-zero-redis
oduflow call get_service_logs inbox-zero-redis 100
oduflow call get_service_info inbox-zero-redis-http
oduflow call get_service_logs inbox-zero-redis-http 100
oduflow call get_service_database inbox-zero
oduflow call inspect_volume inbox-zero-runtime
oduflow call inspect_volume inbox-zero-redis-data
```

To rotate Google or LLM credentials, update `.env` and re-apply the Stack. Do not delete
`inbox-zero-runtime` during an ordinary update.

## Clean up

Stacks never delete resources. Remove them explicitly only after exporting any data you need:

```bash
oduflow call delete_service '{"name":"inbox-zero","save_preset":false}'
oduflow call delete_service '{"name":"inbox-zero-redis-http","save_preset":false}'
oduflow call delete_service '{"name":"inbox-zero-redis","save_preset":false}'
oduflow call delete_environment inbox-zero-stack
oduflow call delete_service_database inbox-zero
oduflow call delete_volume inbox-zero-runtime
oduflow call delete_volume inbox-zero-redis-data
```

Database and volume deletion are permanent.
